# Drone Swarm Control System

A distributed drone fleet simulation built in **C++20**, using **Redis Streams** for asynchronous inter-process communication. The system coordinates autonomous drone agents through a centralized control center, focusing on area coverage, mission scheduling, and battery management.

## Overview

The project simulates continuous surveillance of a 6 × 6 km area using a fleet of autonomous drones.

A central control center manages drone registration, assigns surveillance routes, monitors operational states, and coordinates battery recharging. Individual drone processes communicate with the control center through Redis Streams.

The system was designed to explore distributed communication, resource-constrained scheduling, and coverage optimization under simulated operational conditions.

## Features

- **Fleet coordination** — Centralized mission assignment and monitoring of multiple drone agents.
- **Asynchronous communication** — Redis Streams enable message exchange between independent processes.
- **Coverage tracking** — Grid-based monitoring of surveyed regions and coverage progression.
- **Battery management** — Simulated battery consumption, return-to-base procedures, and recharging cycles.
- **Mission scheduling** — Route assignment and drone coordination based on operational availability.
- **Simulation analysis** — Logging and Python-based visualization of coverage and operational metrics.

## Architecture

The system consists of three main components:

| Component | Responsibility |
|---|---|
| Control Center | Fleet management, mission scheduling, coverage monitoring, and battery coordination |
| Drone Agents | Independent simulation of movement, mission execution, and operational state |
| Redis | Asynchronous message exchange, synchronization, and logging |

The control center and drone agents run as separate processes and exchange messages through dedicated Redis Streams.

Communication is organized into synchronization, drone communication, response, and logging streams.

This separation decouples coordination logic from individual drone behavior.

## Tech Stack

- **C++20** — Simulation engine and control logic
- **Redis Streams** — Inter-process communication
- **CMake** — Build system
- **Python** — Simulation visualization and analysis
- **CSV** — Operational metrics and simulation output

## Getting Started

### Prerequisites

- C++ compiler with C++20 support
- CMake 3.x or later
- Redis Server
- Python 3 (for visualization)

### Build

```bash
cmake -S . -B build
cmake --build build
```

### Run

Start Redis from the project root:

```bash
redis-server --dir ./ --dbfilename dump.rdb
```

Launch the control center:

```bash
./build/control_center
```

In a separate terminal, start the drone simulation:

```bash
./build/drone
```

### Visualization

```bash
cd test
python3 plotter.py
```

*Executable paths depend on the CMake build configuration. The visualization requires simulation output generated by the application.*

## Simulation Parameters

The simulation uses the following operating assumptions:

| Parameter | Value |
|---|---|
| Surveillance area | 6 × 6 km |
| Target revisit interval | 5 minutes |
| Drone speed | 30 km/h |
| Maximum flight duration | 30 minutes |
| Recharge duration | 2–3 hours |
| Target area coverage | 99% |

The system models how fleet size, surveillance requirements, and battery constraints affect the coordination of multiple drones.

These parameters represent simulation requirements, not guaranteed real-world performance.

## Evaluation

The project was evaluated using simulation scenarios of different durations, including runs of 720 and 25,000 seconds.

The analysis focused on:

- Area coverage progression over time
- Drone availability and recharge scheduling
- Fleet size requirements under coverage constraints
- Coordination between the control center and drone processes

Simulation logs and Python-based visualizations were used to examine system behavior and evaluate the surveillance requirements.

The evaluation is limited to a simulated environment and does not represent physical drone testing.

## Limitations

The implementation is a simulation rather than a production drone-control platform. It does not account for physical flight dynamics, environmental conditions, obstacle avoidance, GPS inaccuracies, or network failures.

Its primary focus is software architecture, communication between independent components, and fleet coordination under simulated constraints.
